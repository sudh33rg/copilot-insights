# Evidence-based Copilot usage coaching

Research checked on 2026-10-02. This note informs TraceOn's local, passive coaching; the linked products are references, not dependencies.

## Reading the attached example

The example reports a prompt mix of 58% tool definitions, 25% system instructions and 17% messages. It also reports zero input/output tokens and unavailable credits for that turn. The percentages describe Copilot's recorded composition; they do **not** establish the number of tokens sent, a billed amount, or a saving opportunity measured in credits. The 34.3 seconds of reasoning and three tool rounds identify where to inspect next, but they do not prove waste. A single turn gives no basis for judging the user's prompt quality.

Tool definitions are descriptions and schemas offered to the agent so it can choose tools. Their share can grow when many tools or MCP servers are enabled, when definitions are verbose, or when the user message is short. A high share alone cannot tell which factor caused it. VS Code explains that every model request assembles context from instructions, messages, files and tool outputs, and that a focused tool set limits unnecessary actions and tool output. [Context](https://code.visualstudio.com/docs/agents/concepts/context), [tools](https://code.visualstudio.com/docs/agents/concepts/tools).

## Coaching rules

1. **Prompt quality:** When the opening prompt lacks a target and success condition and the session needs several user turns, suggest a compact next-prompt structure: goal, file or area, constraints, and done-when check. Show the observed turns. A short prompt by itself is weak evidence; do not assign a quality score from length alone.
2. **Corrections and failures:** Count user corrections separately from tool-input retries, failed model turns, and failed tests. Suggest a revised prompt only for corrections or late requirements; investigate errors and tools for failures. Compare within task type, model and similar outcome where the sample is large enough. Correlation does not prove that a prompt caused cost.
3. **Tool definitions:** The latest stored `tools_N.json` snapshot can identify definition names and character sizes. Rank uncalled definitions by size, but say “not called in this session,” not “unused generally.” The snapshot is not linked to each model request, so character-to-token estimates are hypothetical per-request exposure, never an exact session total or credit saving. First action: review the enabled tools/MCP servers in the picker and retain those needed for the task. [Tool sets](https://code.visualstudio.com/docs/agent-customization/tool-sets) can make that choice reusable.
4. **Instructions and context:** If a large system-prompt snapshot exists, suggest moving task-specific rules to scoped instruction files. VS Code supports file-pattern and task-relevance activation. Treat this as an option because built-in system instructions may account for much of the size. [Custom instructions](https://code.visualstudio.com/docs/agent-customization/custom-instructions). Keep explicit file context focused; broad attachments and tool output can increase context. [Context guide](https://code.visualstudio.com/docs/agents/concepts/context).
5. **Credits:** Use Copilot's reported per-request credits only. GitHub says AI credit use depends on model and tokens; lower context may help, but cache rates, model choice and request count change the result. Never multiply a prompt-composition percentage by credits, infer credits from zero-token turns, or promise a percentage saving. [GitHub billing](https://docs.github.com/en/billing/concepts/product-billing/github-copilot-billing), [Copilot session limits](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/set-session-limit).

## Next measurement work

1. Preserve a request identifier and timestamp for each debug prompt artifact, if Copilot emits them. Then compute actual definition exposure per request and separate cached from uncached input. Until then, retain snapshot-level language.
2. Add a local before/after view for tool-set and instruction changes: median input tokens, exact credits when present, first-pass success, corrections and sample sizes, grouped by task type and model. Display “insufficient data” under five comparable sessions. Do not infer causation from a historical comparison.
3. Add a user-controlled outcome mark (“helped / did not help”) to calibrate advice. A token reduction with more failures is not a win.
4. Only after request-level artifact linkage exists, report measured token differences. Credit differences require exact per-request credits and comparable cohorts; any counterfactual remains inferred.

## Acceptance checks for coaching

- The screenshot's zero-token, no-credit case shows a composition explanation and no numeric credit-saving claim.
- Tool advice identifies candidate definitions, labels snapshot provenance and never treats “not called here” as “safe to disable.”
- Prompt advice appears only when the session has relevant prompt findings, and is phrased as a next attempt rather than blame.
- All suggestions remain local; no provider, proxy, or SaaS call is added.
